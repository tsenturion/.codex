# Windows Startup EXE

## Назначение

Этот workflow обновляет локальную копию собранного `.exe`, которая лежит в папке автозагрузки Windows и запускается при входе пользователя в систему.

Skill не привязан к одному проекту. Он применяется к любому репозиторию, где есть понятный способ собрать EXE и установить или скопировать его в:

```text
%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup
```

Обновление локального EXE в автозагрузке не создает, не заменяет и не публикует release-артефакт. Сборка релиза, загрузка артефактов и публикация релиза считаются отдельной задачей.

## Когда запускать

Запускай workflow после:

- значимых функциональных изменений в приложении, фоновом цикле, уведомлениях, tray-поведении, конфигурации, проверках сети, упаковке, установке в автозагрузку или другом исполняемом поведении;
- успешного `git tag push` или push release-тега для проекта, если пользователь явно не сказал не обновлять локальную автозагрузку;
- прямой просьбы обновить локальный EXE в автозагрузке для конкретного проекта.

Не запускай workflow после:

- изменений только в документации;
- правок только README, changelog, комментариев, wording, описаний, метаданных или manifest-файлов без влияния на исполняемое поведение;
- изменений, которые не затрагивают запускаемое приложение.

Если набор изменений смешанный и включает функциональные правки, считай его функциональным и запускай workflow.

## Выбор проекта

Работай из корня проекта, для которого нужно обновить EXE.

Выбирай проект так:

1. Если пользователь указал путь или имя проекта, используй его.
2. Если текущая рабочая директория находится внутри git-репозитория с workflow сборки EXE, используй этот репозиторий.
3. Если контекст указывает на один из известных проектов, используй соответствующий путь:
   - `C:\Users\user\repos\internet-checker`
   - `C:\Users\user\repos\neto`
4. Если несколько проектов подходят и безопасно выбрать нельзя, задай короткий уточняющий вопрос.

Список известных проектов является подсказкой, а не ограничением. Для нового проекта применяй тот же алгоритм обнаружения команд и путей.

## Обнаружение конфигурации

Перед сборкой определи:

- корень проекта;
- команду проверки перед упаковкой;
- команду сборки EXE;
- путь к собранному EXE;
- имя EXE в автозагрузке;
- путь к целевому EXE в Startup;
- команду установки в автозагрузку, если проект ее предоставляет.

Предпочитай уже существующие проектные скрипты и настройки:

- `build_exe.ps1`, `install_startup.ps1`, `package.json`, `pyproject.toml`, `Makefile`, CI-скрипты и README с командами сборки;
- параметры `-SourceExe`, `--source`, `--output`, если они уже поддерживаются проектом;
- путь и имя EXE, явно заданные проектом.

Если проект еще не имеет сборки EXE или установки в автозагрузку, не придумывай workflow за него. Сообщи, что обновление Startup EXE пока невозможно, и укажи, чего не хватает.

Пример для текущего `internet-checker`:

- корень: `C:\Users\user\repos\internet-checker`;
- сборка: `powershell -ExecutionPolicy Bypass -File .\build_exe.ps1`;
- собранный EXE: `dist\InternetChecker.exe`;
- установка: `powershell -ExecutionPolicy Bypass -File .\install_startup.ps1 -SourceExe .\dist\InternetChecker.exe`.

Для `neto` и других проектов используй их собственные команды, когда они появятся.

## Workflow

1. Проверь scope перед сборкой:
   - выполни `git status -sb`;
   - изучи релевантный diff достаточно, чтобы подтвердить, что изменения функциональные;
   - пропусти workflow, если изменения только документационные или описательные.

2. Проверь проект перед упаковкой:
   - запусти проектную проверку, подходящую к изменению;
   - для Python-проекта обычно подходит `python -m py_compile` для входных `.py` файлов или проектный тест;
   - для другого стека используй локально принятый smoke-check, test или lint, если он быстрый и релевантный.

3. Собери EXE:
   - выполни проектную команду сборки;
   - подтверди, что ожидаемый `.exe` появился;
   - не продолжай замену в Startup, если сборка не создала EXE.

4. Определи целевой путь Startup EXE:

```powershell
$startupDir = Join-Path $env:APPDATA "Microsoft\Windows\Start Menu\Programs\Startup"
$builtExe = "<полный или относительный путь к собранному exe>"
$startupExe = Join-Path $startupDir (Split-Path $builtExe -Leaf)
```

Если проектный install-скрипт использует другое имя файла в Startup, используй имя из этого скрипта или настройки проекта.

5. Перед заменой останови только уже установленный EXE из Startup:

```powershell
$startupExe = "<полный путь к exe в Startup>"
$exeName = Split-Path $startupExe -Leaf
Get-CimInstance Win32_Process -Filter "name = '$exeName'" |
    Where-Object { $_.ExecutablePath -eq $startupExe } |
    ForEach-Object { Stop-Process -Id $_.ProcessId -Force -ErrorAction SilentlyContinue }
Start-Sleep -Milliseconds 500
```

Не останавливай все процессы только по имени. Всегда фильтруй процесс по точному `ExecutablePath` в папке Startup.

6. Замени EXE в Startup:
   - если проект предоставляет install-скрипт, используй его;
   - если install-скрипта нет, но путь назначения однозначен, допустимо выполнить прямое копирование после точной остановки процесса:

```powershell
Copy-Item -LiteralPath $builtExe -Destination $startupExe -Force
```

Если install-скрипт дополнительно сам останавливает процессы, копирует EXE и стартует его, все равно сначала выполни точную остановку процесса из Startup, как описано выше.

7. Запусти или проверь только Startup-копию:

```powershell
$startupExe = "<полный путь к exe в Startup>"
$exeName = Split-Path $startupExe -Leaf
$running = Get-CimInstance Win32_Process -Filter "name = '$exeName'" |
    Where-Object { $_.ExecutablePath -eq $startupExe }
if (-not $running) {
    Start-Process -FilePath $startupExe -WorkingDirectory (Split-Path $startupExe) -WindowStyle Hidden
}
```

Не запускай `dist\*.exe` или другой build-артефакт как установленное приложение. Запускаемой локальной версией считается только EXE из папки Startup.

8. Проверь установку:
   - сравни SHA-256 хэши собранного EXE и EXE в Startup;
   - подтверди, что минимум один процесс с нужным именем запущен именно из Startup path;
   - для PyInstaller onefile нормально, если видна parent/child пара процессов с одним и тем же путем EXE.

## Отчет

В финальном ответе укажи:

- какой проект обновлялся;
- была ли обновлена Startup-копия EXE;
- какие проверки запускались;
- совпали ли хэши собранного и установленного EXE;
- запущен ли процесс из точного Startup path;
- что это отдельная локальная операция и она не заменяет release-артефакт.
